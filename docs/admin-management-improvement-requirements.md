# 后台管理系统功能完善需求

## 文档目的

本文记录后台管理系统在正式上线前需要完善的功能、数据规则和验收标准。后台所有新增接口、权限和状态变化，都应同步维护项目 API 文档。

## 一、角色与权限（P0）

当前系统只有管理员和候选人两类身份。后续建议拆分为：

- 超级管理员：用户、权限、系统配置和全部业务数据。
- HR：职位、候选人、初筛、投递流程和 Offer。
- 面试官：分配给自己的面试计划、面试记录和评价。
- 只读人员：仅查看，不允许修改和删除。

每个接口必须在后端校验角色，前端隐藏按钮不能作为权限控制。候选人只能访问自己的简历、投递、面试和通知数据。

## 二、操作审计日志（P0）

新增 `operation_logs` 表，至少记录：

- 操作人、角色、操作时间、IP 和 User-Agent
- 模块和资源类型
- 资源 ID
- 操作类型（创建、修改、删除、状态变更、导出）
- 修改前后的关键字段
- 操作结果和失败原因

候选人状态、简历、JD、面试计划和 Offer 的变更必须写入日志。日志只允许超级管理员查看，不允许普通管理员删除。

## 三、软删除与回收站（P0）

简历、JD、投递记录、面试计划和面试记录默认使用软删除，不直接物理删除。建议增加：

- `deleted_at`
- `deleted_by`
- `delete_reason`

列表接口默认过滤已删除数据；后台提供回收站、恢复和永久删除能力。永久删除必须二次确认并记录审计日志。

## 四、统一 application 主状态（P0）

`application` 是招聘流程主记录，后台页面不得继续通过多个字段自行推断最终状态。建议统一状态：

```text
待初筛 → 初筛通过 → 面试中 → 面试通过 → Offer 待处理 → 已录用
       ↘ 初筛不通过 / 面试不通过 / 已拒绝 / 已取消
```

面试计划和 Offer 作为 application 的子阶段。所有状态迁移必须由后端校验前置状态，禁止跳过初筛直接创建可操作面试流程。

## 五、简历和 JD 数据管理（P1）

后台列表应展示来源、上传时间、解析时间、解析状态、所属候选人、绑定 JD、绑定投递数量和当前使用版本。简历解析失败需要提供重新解析入口，并保留失败原因。

JD 应明确区分草稿、已发布、已暂停、已过期和已关闭。关闭职位时提示对未完成投递的影响，并在候选人端显示职位已关闭。

## 六、统一候选人流程详情（P1）

以 application 详情作为后台主入口，集中展示：

1. 简历和匹配分数
2. 初筛记录
3. 面试计划和面试时间
4. 面试记录与报告
5. Offer 信息
6. 候选人可见反馈
7. 操作日志

内部评价和候选人可见反馈必须分开存储和展示。

## 七、筛选、批量操作与统计（P1）

后台需要支持按招聘类型、JD、状态、来源和时间筛选，并提供批量初筛、批量通知、批量导出。首页统计建议包含投递数、初筛通过率、面试通过率、Offer 发放率和平均处理时长。

## 八、后台开放 API 文档要求

所有后台接口统一维护 OpenAPI 文档，至少包含：

- 请求方法、路径、鉴权要求和角色限制
- 请求参数、响应结构和错误码
- 状态迁移规则
- 删除、恢复、导出等高风险操作说明
- 示例请求和响应

FastAPI 的 `/docs` 仅建议在开发和测试环境开放；生产环境应通过管理员权限、内网或单独的文档认证保护，不能把调试接口无条件暴露到公网。

## 验收标准

- 未授权用户无法调用后台接口。
- 不同角色只能操作授权范围内的数据。
- 删除数据可在回收站恢复，永久删除有审计记录。
- application 状态与候选人端、后台端显示一致。
- 所有关键状态变更可追溯到操作人和时间。
- API 文档与实际接口保持同步。
