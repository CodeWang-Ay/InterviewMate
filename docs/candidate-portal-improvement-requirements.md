# 候选人用户端功能完善需求

## 1. 文档目的

本文档用于记录 InterviewMate 候选人用户端下一阶段的功能完善范围，为产品设计、开发排期、测试验收和上线准备提供依据。

当前用户端已经具备职位浏览、岗位收藏、简历上传与解析、岗位投递、简历初筛、面试流程、Offer 确认和招聘助手等核心能力，主业务流程已经基本闭环。下一阶段重点是补齐账户自助、职位规模化浏览、面试协调、消息通知和跨设备数据能力。

## 2. 当前流程

```text
注册/登录
  → 浏览与收藏职位
  → 上传并解析简历
  → 投递岗位
  → 招聘方简历初筛
  → 创建面试流程
  → 候选人参加各轮面试
  → Offer 发放与确认
  → 招聘流程结束
```

## 3. 需求优先级概览

| 优先级 | 需求 | 主要价值 |
| --- | --- | --- |
| P0 | 候选人账户资料与密码管理 | 保证候选人能够独立维护账户和联系方式 |
| P0 | 职位列表分页或加载更多 | 避免职位超过 20 条后无法浏览 |
| P1 | 面试确认与改期申请 | 补齐真实招聘过程中的时间协调能力 |
| P1 | 站内消息与通知中心 | 让候选人及时获知流程变化 |
| P1 | 招聘助手会话服务端持久化 | 实现跨浏览器、跨设备历史同步 |
| P2 | 候选人可见的流程结果信息 | 提升流程透明度和候选人体验 |
| P2 | 收藏、简历和移动端体验优化 | 完善辅助功能和异常处理体验 |

## 4. 详细需求

### 4.1 候选人账户资料与密码管理（P0）

#### 现状

- 候选人可以上传并持久化头像。
- 候选人姓名、手机、邮箱主要从登录信息或简历解析结果中读取。
- 现有资料修改和密码修改接口主要面向管理员，候选人缺少完整的自助管理入口。
- 登录页缺少忘记密码流程。

#### 功能要求

1. 在个人中心增加“账户设置”入口。
2. 支持候选人编辑姓名、手机号码和电子邮箱。
3. 手机号、邮箱修改后应持久化到候选人资料，并在重新登录后正确显示。
4. 支持候选人通过原密码修改登录密码。
5. 修改密码后应吊销该用户已有登录会话，并要求重新登录。
6. 增加“忘记密码”入口，为后续验证码或邮件重置流程预留能力。
7. 后续可增加账号注销和个人数据导出能力。

#### 验收标准

- 候选人只能修改自己的资料。
- 非候选人身份不能调用候选人资料修改接口。
- 密码长度、手机号和邮箱格式具备基础校验。
- 修改后的资料在退出并重新登录后仍然存在。
- 当前密码错误时不能修改密码，并显示明确提示。

### 4.2 职位列表分页或加载更多（P0）

#### 现状

- 公共职位接口已支持 `page` 和 `page_size`。
- 用户端固定请求第一页、每页 20 条。
- 当某类职位超过 20 条时，用户无法浏览后续岗位。

#### 功能要求

1. 在社会招聘、校园招聘和实习生招聘列表中增加分页。
2. 支持上一页、下一页、当前页和总页数展示，或采用“加载更多”方案。
3. 搜索关键词、职位类别、工作地点、招聘类型和页码应共同生效。
4. 切换筛选条件时页码自动回到第一页。
5. 推荐将筛选条件和页码同步到 URL 查询参数，方便刷新和分享后恢复页面状态。
6. 请求期间应显示加载状态，失败时提供重新加载入口。

#### 验收标准

- 职位超过 20 条时可以访问全部数据。
- 翻页后不丢失当前筛选条件。
- 切换招聘类型或筛选条件后不会停留在无效页码。
- 空列表、最后一页和接口失败状态显示正确。

### 4.3 面试确认与改期申请（P1）

#### 现状

- 候选人可以查看面试时间和当前轮次。
- 满足进入条件时可以进入面试。
- 候选人无法确认是否参加，也无法主动申请调整时间。

#### 功能要求

1. 招聘方设置面试时间后，候选人可以选择“确认参加”。
2. 候选人可以提交改期申请，并填写原因和期望时间段。
3. 招聘方可以同意、拒绝或重新指定时间。
4. 候选人能够查看改期申请的处理状态。
5. 面试临近时提供明确提示。
6. 后续可支持添加到系统日历或生成日历文件。

#### 建议状态

```text
待候选人确认
  → 已确认
  → 申请改期
  → 改期处理中
  → 改期已通过 / 改期已拒绝
```

#### 验收标准

- 只有当前投递对应的候选人可以确认或申请改期。
- 已结束、已取消或尚未排期的面试不能提交改期。
- 招聘方更新结果后，候选人页面无需重新登录即可获取最新状态。
- 所有时间统一保存标准时间，并按照用户所在时区展示。

### 4.4 站内消息与通知中心（P1）

#### 现状

- 流程状态需要进入个人中心后主动查看。
- 缺少统一的未读消息入口和通知历史。

#### 功能要求

1. 用户端导航栏增加消息入口和未读数量。
2. 至少支持以下通知类型：
   - 简历解析成功或失败；
   - 投递成功；
   - 简历初筛通过或不通过；
   - 面试流程创建；
   - 面试时间设置或变更；
   - 面试结果更新；
   - Offer 发放；
   - 招聘流程结束。
3. 通知支持已读、未读和全部已读。
4. 点击通知可以跳转到对应岗位、投递记录或面试轮次。
5. 后续可扩展邮件、短信等外部通知渠道和用户通知偏好设置。

#### 验收标准

- 通知严格按照候选人账号隔离。
- 同一业务事件不会重复生成多条相同通知。
- 未读数量与通知列表状态一致。
- 目标数据被删除或失效时，通知仍可查看，并给出合理提示。

### 4.5 招聘助手会话服务端持久化（P1）

#### 现状

- 招聘助手接口已校验当前登录身份。
- 前端聊天历史按照角色和用户名保存在浏览器本地。
- 清理浏览器数据或更换设备后无法恢复历史记录。
- 点赞、点踩目前只保留当前页面交互状态。

#### 功能要求

1. 增加招聘助手会话和消息数据表。
2. 每个候选人只能访问自己的会话和消息。
3. 支持创建会话、查询会话列表、加载历史消息和删除会话。
4. 支持为助手回复保存点赞、点踩或取消评价状态。
5. 前端本地存储只作为临时缓存，不再作为唯一数据源。
6. 建议限制单次提交的历史消息数量和文本长度，避免上下文无限增长。

#### 建议数据模型

- `assistant_conversations`：会话 ID、用户、标题、创建时间、更新时间。
- `assistant_messages`：消息 ID、会话 ID、角色、内容、时间、反馈状态。

#### 验收标准

- 同一账号更换浏览器后可以读取历史会话。
- 不同账号之间不能读取彼此会话。
- 删除会话需要确认，并同时清理其消息记录。
- 点赞、点踩刷新页面后仍然保留。

### 4.6 候选人可见的流程结果信息（P2）

#### 现状

- 投递时间线可以显示初筛、各轮面试、Offer 和流程结束状态。
- 候选人能够看到通过或不通过，但公开反馈信息较少。

#### 功能要求

1. 每个流程节点显示完成或更新时间。
2. 支持招聘方填写“候选人可见反馈”。
3. 严格区分招聘方内部评价与候选人可见反馈。
4. 显示下一步预计处理时间或“等待招聘方处理”。
5. Offer 阶段支持展示有效期、基本说明和附件下载。
6. 明确面试报告是否允许候选人查看，默认不公开内部完整报告。

#### 验收标准

- 内部评价不会通过候选人接口返回。
- 流程结束后仍保留完整时间线和候选人可见结果。
- Offer 失效或撤回后状态显示准确，历史记录不丢失。

### 4.7 辅助体验优化（P2）

#### 功能要求

1. 增加独立的“我的收藏”完整列表，支持取消收藏和进入岗位详情。
2. 简历解析失败时显示失败原因和“重新解析”入口。
3. 投递记录增加岗位详情入口。
4. 职位关闭或失效后，在收藏列表和历史投递中明确标记。
5. 优化招聘助手、投递时间线和职位筛选在手机端的显示。
6. 统一用户端加载、空状态、错误状态和操作成功提示。

## 5. 非功能要求

### 5.1 权限与数据隔离

- 所有候选人接口必须从后端登录身份获取用户名，不能信任前端传入的用户名。
- 收藏、简历、投递、通知、会话和面试数据必须按候选人隔离。
- 管理员和候选人接口权限应明确分开。

### 5.2 一致性与并发

- 投递、取消投递、Offer 确认和消息生成需要保证幂等。
- 快速双击和网络重试不能生成重复业务记录。
- application 继续作为招聘流程唯一主记录，面试计划、Offer 和通知通过 application 关联。

### 5.3 可用性

- 所有耗时请求应显示加载状态，避免重复提交。
- 错误信息应面向用户描述，不直接展示后端异常堆栈。
- 关键操作使用居中确认框，普通结果使用短时消息提示。

### 5.4 响应式与浏览器兼容

- 以 Chrome 和 Edge 最新稳定版本为主要桌面浏览器目标。
- 支持常见笔记本和大屏分辨率，避免依赖浏览器缩放比例。
- 手机端至少保证职位浏览、登录、投递记录和面试入口可用。

## 6. 建议实施顺序

### 第一阶段：上线前基础能力

1. 候选人资料编辑和修改密码。
2. 职位列表分页。
3. 登录页忘记密码入口和后端流程预留。

### 第二阶段：招聘流程体验

1. 面试确认与改期申请。
2. 站内通知中心。
3. 流程节点时间和候选人可见反馈。

### 第三阶段：智能助手与体验优化

1. 招聘助手会话服务端持久化。
2. 回复反馈数据统计。
3. 收藏列表、异常状态和移动端适配。

## 7. 完成定义

本轮用户端完善工作满足以下条件时，可认为达到正式试用标准：

- 候选人可以独立维护账户资料和密码。
- 所有有效职位均可通过分页或加载更多访问。
- 候选人可以确认面试或申请改期。
- 重要招聘状态变化能够生成候选人通知。
- 投递、面试和 Offer 状态始终以 application 为统一来源。
- 用户数据在不同账号之间严格隔离。
- 关键流程具备后端权限校验、异常提示和基础自动化测试。
